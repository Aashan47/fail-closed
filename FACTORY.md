# Fail Closed

Four seats in which **no seat can both produce evidence and accept it**, and a gate that publishes
what it refused alongside whether refusing mattered.

Work does not advance because an agent said it was finished. It advances because a seat that could
not have written it ran a command against a commit it does not control, and quoted what came back.

## The four seats

| Seat | Edit / Write | Bash | Records a verdict | Opens the gate |
|---|---|---|---|---|
| **Scribe** | denied | allowed (forced) | no | no |
| **Builder** | **allowed** | allowed | no | no |
| **Auditor** | denied | allowed (forced) | **yes** | no |
| **Registrar** | denied | allowed (forced) | no | **yes** |

Exactly one seat may change the work, exactly one produces evidence, exactly one acts on it, and no
seat holds two of those powers. `policy.txt` is the real output of `band runtime template show
--json --reveal` for each seat, generated by `setup.sh`, not written by hand.

This is not Architect / Developer / Reviewer / QA renamed. That roster divides by **job**, which
leaves who may overrule whom undefined, so the line advances whenever the last agent stops
objecting. These four divide by **authority**. The difference is testable: in a job-based roster a
reviewer that also fixes what it found is a helpful reviewer; here it is a contradiction.

`Scribe` turns the task into claims before any code exists and owns `LEDGER.md`. `Builder` is the
only seat that may write implementation code and may never say its own work is correct. `Auditor`
clones at a named revision, runs the claim's command, quotes the output, and throws the clone away.
`Registrar` owns the gate and `REFUSALS.md`, reads verdicts, produces none.

## How the separation is enforced, and exactly how far that goes

Two layers, deliberately unequal. The second is the guarantee. The first is a speed bump, and our
own logs show a seat crossing it.

### Layer 1: runtime tool denial. Real, inspectable, and defeatable.

Each seat is created with Band's per-agent tool policy, for example:

```
band agent create --session auditor --transport claude-code-cli \
  --runtime-auth subscription --cwd <scratch> \
  --claude-disallowed-tool Edit --claude-disallowed-tool Write --claude-disallowed-tool NotebookEdit
```

**`Bash` cannot be denied.** The flag is accepted at creation and then the runtime refuses to start:
`owned Claude Code runtimes cannot deny "Bash": Jam pre-approves jam CLI commands so room
collaboration never waits on a provider prompt`. Band needs a shell to run its own CLI, so every seat
has one, and a seat with a shell can write a file.

That is not theoretical. On the first live run the Scribe, denied every file-editing tool, searched
for one, found none, and routed around the restriction unaided:

> `[thought] Scribe: No file-write tool is exposed in this runtime, so I'll create the ledger with a
> quoted heredoc (literal, no expansion).`

**Tool denial removes the convenient path, not the capability.**

### Layer 2: the Auditor works in a clone it throws away. This is the guarantee.

The Auditor clones at the revision named in the handoff, into its own `--cwd`, and discards it. It
cannot audit uncommitted work, so "it works on my machine" cannot enter the record, and **a shell
does not help it**: anything it writes goes into a directory that is deleted and was never on the
path to the submission. The property that matters, that the seat producing evidence cannot change
what the evidence is about, holds whatever tools the seat has.

Layer 1 still earns its keep. It makes the honest path the obvious one, a reader can check it in
`policy.txt`, and when a seat routes around it the reasoning lands in the room transcript that ships
with this repository. A workaround that has to be argued for in writing, in a log the judge reads, is
a different thing from one nobody can see.

## Why this is not CI with extra steps

The strongest objection to any gated factory is that a required status check on a protected branch
already does this, cannot be bypassed, and needs no agents. **That objection is correct about
enforcement** and this design does not pretend otherwise.

What a required check cannot do is the rest of the loop. A failing check emits a red cross and stops.
It does not decide whether the claim or the implementation was wrong, it cannot route the failure to
whoever owns that authority, and it has one runner with one capability set rather than four
participants with deliberately different ones. A gate enforces; a band negotiates. Remove Band and
you keep the enforcement and lose the loop.

## C-0, which exists because of how entries die

**Every task's first claim is that the service builds and serves from a clean container with no
outbound network by following its own `RUN.md`.** Nothing else is audited until it passes.

A fresh clone is *not* that condition: it still has the network, a warm toolchain, a populated cache
and no resource caps. Auditing in a clone alone would let the factory record a confident pass on
exactly the failure that scores zero. C-0 closes that gap, and it is phrased against `RUN.md` because
that file is what a judge follows, so a `RUN.md` that has drifted is itself the failure C-0 catches.

## The evidence standard is the supplied check, and then what it leaves out

Wherever the task ships checks, the Auditor's command is one of those checks. That alone would be a
trap: the shipped checks are a subset, and on this track they run from 83% of suite 1 down to 9% of
suite 3. A factory that treats a green run as proof has built a machine for passing checks rather
than meeting requirements.

So the Scribe maps the shipped checks and then re-reads the specification to write claims for **what
the shipped checks never asked for**. Those are the most valuable entries in the ledger, and the
Builder is told in as many words that code shaped to pass a check rather than satisfy a requirement
is the worst thing it can do.

## Fail closed, and what it publishes

The gate opens only when every claim has a verdict and every verdict is a pass quoting real output.
Three situations are refusals and are treated identically: a failing verdict, **a claim with no
verdict at all**, and a verdict whose output is empty or paraphrased. The second carries most of the
value, because nearly every pipeline ships on silence and nobody is assigned to notice what was never
checked.

`REFUSALS.md` records each refusal with a column almost nobody publishes: **would this have failed
the graded suite?** On every FAIL the Auditor runs the graded suite at the same revision, so the
answer is two recorded runs rather than an opinion. A `yes` means the gate caught what the grader
would have caught. A `no` is the more interesting case, because the gate caught something the
supplied checks do not test for. `unknown` is reserved for refusals about evidence provenance rather
than defects.

## What it cost

Measured with `band usage rooms`, which attributes per room and splits per seat. These are
**estimates at list prices, not a bill**: the seats run on a subscription, so no money changed hands.

| Run | Total | Per seat |
|---|---|---|
| First rehearsal | $184.44 | builder $52.60, registrar $48.60, scribe $43.77, auditor $39.46 |
| Stage 1 | $57.86 | builder $21.07, scribe $16.35, auditor $10.28, registrar $10.15 |
| Stage 2 | **$40.16** | builder $18.43, auditor $8.65, scribe $8.55, registrar $4.53 |

Two things in that table are worth more than the totals.

**The trend runs the wrong way on purpose.** $184 to $58 to $40 across runs of *increasing* scope.
The early spend was not work, it was seats re-establishing context and re-litigating lost evidence.
Every dollar saved came from a mandate change, not a model change.

**The split is independent evidence of the separation.** The Builder costs roughly twice the Auditor
and the Registrar is cheapest, which is what a division by authority should cost: the seat that
writes does the most work, the seat that decides does the least. A factory where those four numbers
were equal would be four agents doing the same job under different names.

Measured elapsed time, stage 2 of the development run, dispatch to gate close: **2h 4m 39s**, cited
between two commits. Its ledger held 84 claims with 51 verdicts committed, 50 of which passed first
time.

## What broke, and what each break changed

Four flaws, none found by review, all found by running it.

**1. `Bash` cannot be denied.** The design claimed infrastructure enforcement while the runtime
silently accepted a flag it would later refuse to start with. Two of four seats were dead on arrival
and `setup.sh` would have failed for anyone who ran it. **Changed:** the enforcement claim was
demoted to a speed bump and the discarded clone promoted to the guarantee.

**2. Verdicts died with a session.** Band's API closed connections mid-response; restarting the seats
wiped everything the Auditor held, so it could not resend verdicts it had genuinely produced, and the
Registrar correctly refused the paraphrases. The gate behaved perfectly and the design was wrong.
**Changed:** the Auditor commits `verdicts/<claim-id>.md` before posting. A verdict that exists only
in context is a memory, not evidence.

**3. Nobody owned the queue.** The band deadlocked with the Builder reporting "no claim is currently
open for me" while the Scribe owned claims and the Registrar owned verdicts. All three were obeying
their mandates and the work still stopped. This is the characteristic failure of a clean separation:
divide authority sharply enough and you can create a gap nobody is responsible for. **Changed:** the
Builder self-dispatches, and the idle condition is spelled out so waiting silently is named as a
misreading.

**4. A silent stall looks like a healthy factory.** Seats reported `presence=live binding=bound`
while processing nothing for ninety minutes. **Changed:** a watchdog restarts seats after ten
minutes of silence with queued messages, and a supervisor wakes a human only for decisions.

## Standing it up on a different problem

Nothing in `mandates/` names this challenge, this track or anything the task asked for.

```
OWNER=<your-band-handle> [WORKSPACE=<path>] ./setup.sh
```

That creates the four seats with the tool policies above, binds each mandate, and writes
`policy.txt`. Then paste a task into the room and address the Registrar. The specifics of a problem
live in the room and on the board, never in a seat's standing instructions.

One portability note found the hard way: `--instructions-file` makes the daemon read the path itself,
so it times out after five seconds under macOS TCC-protected directories such as `~/Desktop`.
`setup.sh` pipes mandates on stdin instead.

## Honest limits

- **Tool denial is not a sandbox, and `Bash` cannot be removed.** The guarantee is the discarded
  clone. Docker Sandboxes would close the gap properly and were checked: `band runtime
  sandbox-support` reports `"installed": false` on this machine.
- **The Auditor is only as good as the check**, and where no graded suite covers a claim it is only
  as good as the command the Scribe wrote.
- **Fail-closed stalls rather than guesses.** Intended, and still costly near a deadline.
- **The refusal count is not a quality score.** Only the counterfactual column separates a careful
  gate from a careless builder. In the development run that column was entirely `unknown`, because
  every refusal was about evidence provenance rather than a caught defect. **On that run the gate was
  not shown to pay for itself**, and the measurement that would settle it was added afterwards.
- **A clone and a container per handoff cost wall-clock time**, and on a larger repository this
  design would need caching.
- **Handoffs name seats directly.** A more general factory would resolve them by capability at
  runtime.
